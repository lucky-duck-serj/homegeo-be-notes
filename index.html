Две правки be

PR 1 · add-dwelling-change-log

Журнал изменений каталога и роль только для чтения

Что
Триггеры на 21 таблице каталога пишут в bot_catalogchange строку «таблица, ID строки, операция, тип сделки, ID объекта, ID транзакции» в той же транзакции, что и само изменение. Роль platform_adapter читает журнал и разрешённый список столбцов по закрытому сетевому пути. Задача huey раз в сутки удаляет строки старше 7 дней.
Зачем
Адаптеру нужно знать о каждом изменении того, что видит клиент, без потерь. Сегодня надёжного сигнала нет: updated_at не двигается массовым update() и SQL руками, цена живёт в строках партнёров, фото и переводы в своих таблицах, удаление не оставляет следа.
Что меняет в be
Ни одного ответа API, бота, Mini App и админки. Плюс одна строка журнала на каждую изменённую строку каталога, короткая блокировка таблиц при создании триггеров, первая периодическая задача huey, первые тесты репозитория.
PR 2 · add-site-client-service-api

Служебный API для клиентов сайта

Что
Семь методов под /service/v1 за ключом Authorization: Bearer: найти или создать профиль по tg_id; прочитать, поставить и снять отметку (избранное, «не нравится», «просмотрено»); прочитать, сохранить и остановить поиск.
Зачем
Клиент входит на сайт через Telegram (клиент входа это бот be) и должен видеть те же отметки, что в Mini App, сохранять поиск, а бот be должен присылать по нему новые объекты. Адаптер в таблицы be сам не пишет.
Что меняет в be
«Добавить в избранное» в Mini App теперь снимает «не нравится»; лайк и дизлайк стали одной транзакцией с блокировкой профиля; гонки, которые давали 500, получили коды; без ключей методы отвечают 404. Миграций нет.

Граница одна. Данные объектов адаптер читает из базы be сам: только чтение и только по списку столбцов. Всё о людях (профили, отметки, поиск) идёт только через методы be. У роли базы нет ни одного идентификатора человека, даже Telegram ID.

Механика репликации

«Маленькая база у фронтенда» это витрина: копия опубликованных объектов в SQLite у каждой копии сайта (файл node:sqlite на Node, позже Durable Object в Cloudflare). Страницы читают только её, поэтому сайт ищет и отвечает, даже когда be и адаптер лежат.

Изменение проходит пять звеньев. На каждом переходе у читателя своя позиция, которую он сохраняет той же транзакцией, что и результат. Поэтому простой любого звена ничего не теряет: после возвращения читатель продолжает со своей позиции.

Звено 1 Запись в be попадает в журнал

  • На каждой из 21 таблицы два триггера: AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW с аргументами «тип сделки» и «столбец с ID объекта», и AFTER TRUNCATE … FOR EACH STATEMENT (построчный на TRUNCATE не срабатывает). Таблицы: объекты, партнёры, фото, переводы, связи с удобствами (аренда и продажа), удобства, жилые комплексы, районы, станции, города, их переводы, языки.
  • Строка журнала: id, xact_id (xid8, pg_current_xact_id()), changed_at, table_name, row_id, op, deal, dwelling_id. Значений строки нет: текущее состояние читатель берёт из таблиц, поэтому через журнал не утечёт столбец, который роли читать нельзя.
  • Перенос строки к другому объекту пишет две строки (старый и новый объект). Изменение без новых значений тоже пишется: Django save() всё равно трогает updated_at, лишнюю ревизию потом отсекает хэш у адаптера.
  • Каскадное удаление делает Django (on_delete=CASCADE), у внешних ключей в базе каскада нет. Каждая удалённая зависимая строка попадает в журнал со своим ID объекта.
  • Функция называет журнал со схемой (иначе сессия с другим search_path падала бы на записи) и не читает других таблиц, поэтому не может попасть во взаимную блокировку с приложением.
  • Журнал не видит: ALTER TABLE … DISABLE TRIGGER и сессии с session_replication_role = replica (восстановление дампа, логическая репликация).

Звено 2 Адаптер читает журнал

  • Опрос раз в несколько секунд, только основной базы (на реплике правило не проверено), ролью platform_adapter по закрытому пути. Позиция это пара (xact_id, id), читается только то, что ниже горизонта (самой старой ещё открытой транзакции):
SELECT id, xact_id, table_name, row_id, op, deal, dwelling_id
FROM bot_catalogchange
WHERE (xact_id, id) > (:last_xact_id, :last_id)
  AND xact_id < pg_snapshot_xmin(pg_current_snapshot())
ORDER BY xact_id, id
LIMIT 1000;
  • Почему не просто id > позиции. ID строки выдаётся при вставке, а транзакции фиксируются в другом порядке. Транзакция A вставила строку 10 и ещё открыта, B вставила 11 и зафиксировалась: читатель по id прочитает 11, сдвинется, и строку 10 не увидит никогда (опыт на PostgreSQL 13, 14, 15 и 16).
  • Позицию адаптер хранит в своей базе, той же транзакцией, что пересобранные документы.
  • С каждой пачкой, в той же картине базы, две проверки. Позиция не раньше bot_catalogchange_pruned: иначе очистка удалила непрочитанное, нужен полный проход. xact_id позиции не выше pg_snapshot_xmax(…): иначе базу восстановили на новый сервер, счётчик транзакций ушёл назад, нужен полный проход.
  • Полный проход: запомнить горизонт H, прочитать каталог целиком (можно несколькими транзакциями), сохранить результат с позицией (H, 0). Всё, что шло во время прохода, имеет xact_id ≥ H и будет прочитано ещё раз из журнала, а повторная пересборка безвредна. Проход идёт при первом старте, после потери строк, после строки truncate (по этой таблице) и раз в час для сверки (ловит выключенный триггер). Пока журнала в be нет, адаптер живёт полными проходами раз в 5 минут.
  • Очистка: задача huey раз в сутки удаляет пачками строки старше 7 дней и ниже горизонта и тем же запросом двигает позицию последней удалённой строки. Время последнего успешного запуска пишется в last_run_at, тревогу на него ставит адаптер (своих метрик у be нет).

Звено 3 Адаптер собирает документ объекта

  • По каждой строке журнала адаптер пересобирает затронутый объект в homegeo.catalog.v1.Listing. Опубликован, если is_active и есть хотя бы один партнёр; иначе в ленту идёт снятие REASON_UNPUBLISHED (причину снятия be не различает).
  • Цена, залог и минимальный срок от партнёра с самой низкой ценой (затем sort_num). Районы и станции переводятся в ключи мест платформы таблицей соответствия адаптера; объект с неотображённым районом не публикуется. Точка своя, иначе жилого комплекса. Порядок и published_at из last_activated_at.
  • Публичный код: 8 цифр (7 случайных и контрольная Дамма), выдаётся при первом появлении и не меняется. Номер объекта be наружу не выходит.
  • Фото копирует отдельное задание: из хранилища be в R2, ширины 480, 960, 1600 в AVIF и WebP, имя по SHA-256. Пока фото не скопировано, объект публикуется без него.
  • Ревизия растёт, только когда меняется хэш документа. Запись в be, которая не меняет видимого клиенту, в ленту не попадает.

Звено 4 Лента каталога адаптера

  • Таблица ленты в PostgreSQL адаптера: одна строка на объект. Изменение переносит строку в конец, поэтому чтение с пустого курсора отдаёт каждый объект один раз, в текущем состоянии. Сборка нового читателя, догон после простоя и сверка это один и тот же вызов.
  • Позиции выдаёт отдельная работа уже после фиксации, под арендой и с замком на голову ленты. Это та же проблема поздней фиксации, что в звене 2, но решена одиночкой: в своей базе мы его себе позволяем, а в be не хотим держать ни одного процесса.
  • Changes(cursor, limit, wait): Connect, метод GET (без побочных эффектов). Ответ: записи ListingChange (код, ревизия, Listing или Withdrawal), next_cursor, флаг restart. С wait до 25 с вызов ждёт изменений; ждущие вызовы будит LISTEN в базе адаптера (там мы единственный слушатель).
  • Эпоха лежит в курсоре: если базу адаптера восстановили из копии, курсор старой эпохи получает restart. Следы снятых хранятся 90 дней; курсор старше тоже получает restart.

Звено 5 Сайт применяет ленту в витрину

  • Шаг feedStep в ядре сайта: прочитать feed_state, вызвать Changes, применить пачку, вернуть паузу. На Node его крутит цикл на setTimeout, в Cloudflare будильник Durable Object.
  • Пачка и курсор в одной синхронной транзакции SQLite. По каждой записи: ревизия не новее сохранённой, пропустить (идемпотентность); проверить документ (код из 8 цифр с контрольной, числа до 253, цена строкой, хранится в сотых); опубликованное: INSERT … ON CONFLICT(id) DO UPDATE … WHERE excluded.revision > listing.revision и точка в R*Tree; снятое: строка уходит в listing_withdrawn (след на 90 дней для страницы 410 и похожих).
  • Плохая запись не останавливает ленту: она уходит в feed_failures, курсор идёт дальше, следующее хорошее состояние того же объекта закрывает отказ. После трёх падений пачки подряд шаг идёт «по одной» (limit 1), потому что у записи нет своего курсора.
  • Паузы: при сборке и полной пачке 0; в обычной работе 1 с после долгого опроса; ошибки сети от 1 с с удвоением до 60 с; отказ в доступе 60 с и запись в журнал.
  • Пересборка без простоя. На restart или миграцию схемы шаг наполняет listing_new и соседние таблицы с пустого курсора, пока старые отвечают на запросы; после догона одной транзакцией меняет таблицы местами (DROP, RENAME, CREATE INDEX, ANALYZE). Опыт: 50 000 объектов с карточкой около 10 КБ наполняются за 1,7 с, подмена 0,25 с, файл 0,8 ГБ.
  • Каждая копия сайта это отдельный читатель: свой файл, свой курсор, без аренды. На запуске копий две, значит два долгих опроса к адаптеру.
  • Готовность (решение пользователя 2026-11-13, «вариант Б»): собранная копия готова после догона ленты при старте или после 60 с недоступности платформы; несобранная не готова никогда, поэтому пустая выдача не уходит в CDN.

Плюсы и минусы выбранного пути

Плюсы

  • Изменение не пропускается: триггер в той же транзакции видит массовые update(), SQL руками, каскадные удаления, изменения партнёров, фото и переводов.
  • be никого не вызывает и не знает о читателях; ответы API, бота, Mini App и админки не меняются.
  • Данные людей не уходят: журнал без значений, роль по разрешённому списку столбцов, права проверяются скриптом по действующим правам базы.
  • Каждое звено читает со своей позиции: простой любого звена ничего не теряет.
  • Сайт не зависит от be во время запроса: страницы читают локальный SQLite, выдача быстрая и работает при упавших be и адаптере.
  • Переход на CRM для сайта это смена адреса и одна пересборка.
  • В обычной работе цена для be мала: одна вставка около 190 байт на изменённую строку.
  • Отметки стали честнее и для Mini App: избранное и «не нравится» больше не совпадают, гонки не оставляют обе отметки или ни одной.

Минусы и цена

  • Упавшая вставка в журнал роняет запись в be. Это единственный путь навредить be, поэтому функция минимальна и на каждую таблицу есть тест.
  • Массовые запросы медленнее примерно вдвое: 100 000 объектов за 1,7 с против 0,85 с (ноутбук, PostgreSQL 16.1).
  • Задержка в секунды, а не в доли секунды: без NOTIFY.
  • Одна долгая пишущая транзакция где угодно на сервере PostgreSQL останавливает ленту.
  • Адаптер читает таблицы be по именам столбцов: это неявный контракт со схемой be.
  • Нужна работа команды be вне кода: роль и пароль, закрытый путь, ключи, huey на stage, окно выкладки.
  • Цепочка длинная (журнал be, лента адаптера, витрина), у каждого звена свои позиции и правила восстановления: больше кода и тестов.
  • Каждая копия сайта читает ленту сама: N копий дают N долгих опросов и N полных проходов при пересборке; на время пересборки место на диске удваивается.

Подводные камни

Отмечено, насколько больно, если камень сработает, и что уже сделано или предложено.

Журнал и роль (PR 1)
высокий

Горизонт общий для всего сервера PostgreSQL, а не для одной базы.

Транзакция с ID транзакции в другой базе того же сервера (например, stage рядом с production) держит читателя production. Держат и SELECT … FOR UPDATE / FOR SHARE, и подготовленные транзакции; обычный SELECT не держит.

Что делаем: метрика и тревога на возраст непрочитанной строки. Нужен ответ: один ли сервер у stage и production, бывают ли ручные сессии psql.

высокий

Восстановление базы be на новый сервер или на точку во времени.

Счётчик транзакций идёт назад, новые строки получают xact_id ниже позиции адаптера, и запрос их не вернёт никогда.

Что делаем: сравнение с pg_snapshot_xmax на каждой пачке и часовая сверка. В design адаптера этой проверки пока нет (раздел «Что поправить у нас»).

высокий

Очистка удаляет строки прямо впереди читателя посреди догона.

Если сравнивать позицию с удалённой один раз перед серией пачек, читатель перешагнёт дыру и не заметит потерю (опыт 11).

Что делаем: сравнение с каждой пачкой, в картине базы самой пачки.

средний

Запись мимо триггера.

DISABLE TRIGGER, session_replication_role = replica (pg_restore, логическая репликация) не оставляют строк в журнале.

Что делаем: check_catalog_log после каждой выкладки, часовая сверка у адаптера.

средний

Блокировка таблицы журнала останавливает все записи в каталог.

Режим SHARE и сильнее (CREATE INDEX без CONCURRENTLY, VACUUM FULL, ALTER TABLE) заставляет ждать каждую запись в таблицы каталога. Обычный VACUUM безопасен.

Что делаем: такие работы только вне часов работы сотрудников; спросить про регламентные работы be.

средний

Блокировки при выкладке триггеров.

CREATE TRIGGER ждёт открытые пишущие транзакции и задерживает новые записи; оба ожидания с ограничением не дождутся друг друга (опыт 7).

Что делаем: неатомарная миграция, каждый триггер в своей транзакции с lock_timeout 2 с и повтором, миграцию можно запустить снова; тихое окно.

средний

Будущие миграции be ломают адаптер молча.

Переименование или замена таблицы каталога должны перенести триггер. Переименование столбца не ловит ни проверка, ни права, а SQL адаптера сломается.

Что делаем: check_catalog_log ловит триггеры. Для столбцов нужна договорённость с командой be.

средний

Изменение справочной строки касается многих объектов.

Координаты или название жилого комплекса, название района: в строке журнала dwelling_id пуст. Адаптер должен сам найти и пересобрать зависимые объекты.

Что делаем: в design адаптера это не расписано (раздел «Что поправить у нас»).

низкий

Первая периодическая задача huey в be, а на stage потребитель не запущен.

1

Источник изменений: триггеры и журнал в базе

решениефакт

Устраивает ли вас, что сигнал об изменениях дают триггеры базы, а не код приложения? Есть ли места, где каталог меняется мимо Django: скрипты, импорты, pg_restore, ручной SQL?

Варианты и почему выбрали
  • Опрашивать updated_at. Не видит массовых update(), SQL руками, изменений партнёров, фото, переводов и удалений. Так адаптер работает, пока журнала нет: полный проход раз в 5 минут.
  • Сигналы Django или HTTP-вызов из be. Не видят массовых операций и SQL руками, теряются, пока читатель лежит, и заставляют be вызывать платформу.
  • Outbox в коде Python. О нём должен помнить каждый пишущий; массовые действия админки и миграции не вспомнят.
  • Логическая репликация или Debezium. Слот репликации и настройка сервера; без читателя может остановиться очистка WAL; отдаются целые строки, вместе с телефоном собственника.
  • Триггеры на запрос с переходными таблицами. Дешевле для массовых запросов, но три триггера на таблицу вместо одного. Запасной вариант, если замер массовых запросов будет плохим.
  • Выбрано: построчные триггеры пишут в журнал только «что и где изменилось», в той же транзакции.

Почему: единственный вариант, который видит все пути записи и не несёт значений строк; be ничего не вызывает и не держит ни одного нового процесса для правильности.

Только опрос, без NOTIFY

решение

Устраивает ли задержка в несколько секунд? Пользуется ли сейчас кто-то LISTEN/NOTIFY на сервере be?

Варианты и почему выбрали
  • NOTIFY рядом с журналом. Задержка в доли секунды, первый проект платформы на это рассчитывал.
  • Выбрано: только опрос раз в несколько секунд по индексу; почти всегда возвращает пустой ответ.

Почему: очередь уведомлений одна на весь сервер (по умолчанию 8 ГБ); слушатель, застрявший в транзакции, останавливает её очистку, и при полной очереди падает каждая фиксация с уведомлением, то есть рискуют пишущие be. Транзакцию с NOTIFY нельзя подготовить к двухфазной фиксации. Для правильности он не нужен, а страницы и так кэшируются на 5 с. Добавить можно позже одной миграцией функции. В своей базе адаптер NOTIFY использует: там он единственный слушатель.

Выкладка триггеров

операция

Как у вас идут миграции на production (сами при выкладке или руками)? Какое окно тихое? Подходит ли lock_timeout 2 с с повтором?

Что предложено

CREATE TRIGGER берёт блокировку таблицы, которая ждёт открытые пишущие транзакции и задерживает новые записи. Поэтому миграция неатомарная: каждый триггер в своей короткой транзакции с ограничением ожидания, неудачный повторяется, миграцию можно запустить снова. Порядок: копия production, stage, production в тихий час, затем закрытый путь. Откат: обратные миграции и обратный скрипт роли, данные каталога не трогаются.

Будущие миграции таблиц каталога

решение

Как договоримся, чтобы миграции be, которые переименовывают таблицы или столбцы каталога, не ломали адаптер молча? Запускать check_catalog_log в CI be? Предупреждать нас о таких миграциях?

Почему это важно

Проверка ловит потерянный или выключенный триггер и роль, которая пишет в каталог, но не в журнал. Но адаптер читает столбцы по именам: переименование столбца не поймает ни проверка, ни права, а новый столбец адаптер не увидит, пока его не выдадут роли намеренно. Это неявный контракт со схемой be.

Общая функция отметок и изменение Mini App

решениефакт

Согласны ли вы, что «добавить в избранное» в Mini App теперь снимает «не нравится»? Переводить ли «убрать из избранного» и «просмотрено» на общую функцию сейчас или позже? Сколько сейчас объектов, которые у одного профиля и избранные, и «не нравится» (задача 0.5)?

Варианты и почему выбрали
  • Оставить Mini App как есть, правило только в служебных методах. Два правила для одного человека, и гонки остаются.
  • Одна транзакция на действие без блокировки. Две такие транзакции не видят новые строки друг друга и оставляют обе отметки (воспроизведено SQL).
  • Выбрано: set_mark под transaction.atomic() с SELECT … FOR NO KEY UPDATE на строке профиля.

Почему: двое пишущих для одного человека идут друг за другом, откуда бы ни пришли. FOR NO KEY UPDATE, а не FOR UPDATE: не мешает вставкам других строк, которые ссылаются на профиль (заметки, предложения цены). Сегодня четыре отдельные записи лайка и дизлайка в порядке «добавить, добавить, снять, снять» оставляют объект без отметок.

Что предложено

Флагом владеет админка; вход ничего не меняет у такого профиля (ни имя, ни язык), команды и чтения отвечают access_denied. Рассылка новых объектов на флаг сегодня не смотрит, и правка это не меняет.

решение

Перерисовывать сообщения бота с фильтром после сохранения поиска с сайта, как это делает Mini App, и не ронять вызов при неудаче?

Что предложено

Общая функция save_profile_search перерисовывает до пяти запомненных сообщений после фиксации и перехватывает любую неудачу (Telegram, Redis). Для Mini App это превращает ошибку после уже сохранённого поиска в успех.

lock_timeout у процесса API

решениеоперация

Готовы ли поставить lock_timeout (предложено 5 с) в настройки соединения процесса API? Есть ли вызовы API, которые по делу ждут блокировку дольше?

Почему это важно

Запрос, ждущий чужую блокировку, занимает единственный синхронный поток процесса, и ждут все вызовы, включая Mini App и вызов с неверным ключом. Замер на PostgreSQL 16.1: вызов без базы ждал больше 8 с; с lock_timeout=1s застрявший падал через секунду, остальные отвечали за полсекунды. Проблема есть и сегодня, правка её не создаёт.
