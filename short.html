Две правки be коротко

Какое решение принято и почему, какие были альтернативы, риски и плюсы. Подробности, механика и вопросы к команде be в полной памятке. Состояние на 13.11.2026: обе правки реализованы и покрыты тестами, не выложены, ждут ревью команды be.

Общая картина. Запись в be → строка журнала в той же транзакции → адаптер опрашивает журнал и пересобирает объект → лента каталога → каждая копия сайта пишет её в свою SQLite (витрину) → страницы. От правки в админке до страницы обычно 5-10 с; сайт отвечает по витрине, даже когда be и адаптер лежат.

1 Журнал изменений каталога

Решение. Триггеры на 21 таблице каталога be в той же транзакции пишут в журнал строку «таблица, ID строки, операция, объект, ID транзакции», без значений. Адаптер опрашивает журнал раз в несколько секунд ролью только для чтения, видящей разрешённый список столбцов. Журнал хранится 7 дней.

Почему. Сегодня у be нет надёжного сигнала: updated_at не двигается массовым update() и SQL руками, цена живёт в строках партнёров, фото и переводы в своих таблицах, удаление следа не оставляет. Триггер видит все пути записи, а be при этом никого не вызывает.

Альтернативы
ВариантПочему нет
Опрашивать updated_atНе видит массовых правок, SQL руками, партнёров, фото, переводов и удалений
Сигналы Django или HTTP-вызов из beНе видят массовых операций, теряются, пока адаптер лежит; be пришлось бы вызывать платформу
Outbox в коде PythonО нём должен помнить каждый пишущий; массовые действия админки и миграции не вспомнят
Логическая репликация, DebeziumСлот и настройка сервера, риск для WAL без читателя, отдаёт целые строки с телефонами собственников
Уведомления NOTIFYОчередь общая на сервер: при переполнении падают фиксации у пишущих be. Выигрыш в секундах не нужен, страницы кэшируются на 5 с
Читать по id > позицииТеряет поздно зафиксированные транзакции; читаем по паре «ID транзакции, ID строки» ниже горизонта

Риски

  • Одна долгая пишущая транзакция на сервере PostgreSQL, даже в соседней базе, останавливает ленту. Ничего не теряется, но сайт отстаёт.
  • После восстановления базы be на новый сервер адаптер перестаёт видеть изменения, если не сверяет позицию с pg_snapshot_xmax. В design адаптера этой проверки пока нет.
  • Адаптер читает столбцы be по именам: миграция be с переименованием сломает его молча. Нужна договорённость с командой be.
  • Массовые запросы примерно вдвое медленнее (100 000 объектов: 1,7 с против 0,85 с); упавшая вставка в журнал роняет и саму запись.
  • Запись мимо триггера (DISABLE TRIGGER, загрузка дампа) ловит только часовая сверка.
  • Тяжёлое обслуживание таблицы журнала (VACUUM FULL, индекс без CONCURRENTLY) останавливает все записи в каталог.

Плюсы

  • Изменение не пропускается: массовые правки, SQL руками, каскадные удаления, партнёры, фото, переводы.
  • be не знает о читателях и никого не вызывает; ни один ответ API, бота, Mini App и админки не меняется.
  • Данные людей не уходят: в журнале нет значений, роль видит только разрешённые столбцы.
  • Простой любого звена ничего не теряет: каждое читает со своей позиции.
  • Переход на CRM для сайта это смена адреса и одна пересборка витрины.

2 Служебный API для клиентов сайта

Решение. Семь методов be под /service/v1 за служебным ключом: найти или создать профиль по Telegram ID, прочитать, поставить и снять отметку, прочитать, сохранить и остановить поиск. Правила отметок и поиска собраны в общих функциях, которыми пользуется и Mini App.

Почему. Клиент сайта входит через Telegram и должен видеть те же отметки, что в Mini App, а бот be должен присылать новые объекты по поиску с сайта. До CRM профили, отметки и поиск живут в be, и владелец решил, что адаптер пишет туда только через методы be.

Альтернативы
ВариантПочему нет
Адаптер пишет в таблицы be самПравилами владели бы две программы; миграция be ломала бы адаптер молча
Адаптер читает отметки ролью базыРоль получила бы Telegram ID клиентов и их отметки
API Mini App с initDataУ сайта нет initData, а у нового человека нет профиля
be сам проверяет вход Telegrambe понадобились бы секрет входа и правила сессии сайта
ID запроса и память вызовов в beНовая таблица и её очистка; порядок команд и так держит адаптер
Отдельное приложение для методовЛишний процесс, образ и шаг выкладки ради семи методов (вопрос открыт для команды be)

Риски

  • В процессе API be один запрос, ждущий чужую блокировку, останавливает все вызовы, включая Mini App (замер: больше 8 с). Правка это не создаёт, но добавляет трафик; предложен lock_timeout.
  • be не помнит порядок вызовов: старая команда, повторённая после новой, вернёт старое состояние. Адаптер обязан слать команды клиента по одной.
  • Меняется Mini App: «добавить в избранное» теперь снимает «не нравится».
  • Профилю с сайта ставится язык сайта, и бот потом не спрашивает язык.
  • Узнать, разрешил ли человек боту писать, нельзя: сайт всем показывает подсказку открыть бота.

Плюсы

  • Всё о клиентах за одним входом: в базе адаптер не видит ни одного идентификатора человека.
  • Правила отметок и поиска в одном месте для сайта и Mini App.
  • Закрыты гонки, которые сегодня оставляют объект с двумя отметками или без них, и ошибки 500 на двойном клике.
  • Повтор вызова безвреден; без ключей методы отвечают 404, а откат правки ничего не ломает в данных.
